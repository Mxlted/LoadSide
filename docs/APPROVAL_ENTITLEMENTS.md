# Entitlements requiring Apple approval

Reviewed against public Apple documentation on **2026-10-12**. This catalog contains **113 exact entitlement keys**, researched through 267 Apple entitlement/index pages and the linked program guides. It covers the documented managed programs found in that review, not just the supplied IPA.

LoadSide omits an unauthorized cataloged claim in both Strict and Compatible, logs its capability name and key, and preserves a claim when the profile authorizes its value. “Distribution only” entries use this exception for distribution profiles; a Development profile still follows the selected policy for missing authorization. This does not replace profile, certificate, identity, device or platform validation. Entries for Mac-only programs do not enable signing macOS code inside an IPA.

Apple does not publish a guaranteed exhaustive machine-readable approval registry. Some programs are private or account-specific, and requirements change. Unknown keys stay under Strict/Compatible rather than being guessed from a prefix, a missing profile entry, or an App Store review requirement. Every classification below has a primary source; the code stores the same evidence URLs for maintenance. Do not classify user permission prompts as Apple approval.

## Boundaries and changes in Apple requirements

- Family Controls and Manage Thread Network Credentials explicitly provide development access before distribution approval. Xcode 14 added automatic development signing for DriverKit; distribution still requires approval. DriverKit PCI, block storage, virtual HID and UserClient access retain managed-access classification where Apple exposes a request flow without a self-service development counterpart. Foundation Models custom adapters need approval for deployment, not local training/testing, so their exception is distribution-only.
- HealthKit Access only omits the unauthorized `verifiable-health-records` array item; ordinary `health-records` still follows Strict/Compatible. Fonts only omits `font-enumeration`; `app-usage` and `system-installation` remain ordinary. Authorized items remain even if another item is omitted, and malformed arrays do not trigger the exception.
- Deep Submerged Depth and Pressure is managed; ordinary Shallow Depth and Pressure is not.
- Ordinary App Groups, Associated Domains, Push Notifications, Siri, Wi-Fi information, default calling/messaging/navigation/translation, Critical Messaging, ID Verifier - Display Only, and regular NFC tag reading are not classified merely because their APIs require user consent, regional eligibility, or App Review. Identity, keychain and debugger claims remain subject to their existing checks.
- The browser-engine group includes its documented companion extension and memory-transfer keys. Generic `com.apple.security.cs.allow-jit`, extended virtual addressing, and hardened-runtime keys are not classified from that association because other apps use them without that approval.
- The iPadOS DriverKit client capabilities `com.apple.developer.driverkit.communicates-with-drivers` and `com.apple.developer.driverkit.allow-third-party-userclients` remain ordinary checks; the cited driver-request guide does not establish separate approval for them.
- `com.apple.developer.family-controls.app-and-website-usage` documents user authorization and an ordinary capability toggle; it is not automatically treated as Family Controls distribution approval.
- Nearby Interaction DL-TDOA [no longer requires an entitlement in iOS 27](https://developer.apple.com/documentation/nearbyinteraction/dl-tdoa-ranging). It is not classified from the older portal label alone.
- FileProvider Testing Mode is development-only, not a capability Apple grants for distribution on request; it is not put in this approval catalog.
- The supplied IPA's `com.apple.developer.coremedia.allow-alternate-video-decoder-selection` and `com.apple.developer.storekit.request-data` have no verified public approval mapping. They remain under Strict/Compatible. The latter is not any of the documented StoreKit purchase/link entitlements.
- Pass presentation suppression and payment-pass provisioning use Apple's archived entitlement reference because the current reference lacks the approval detail. Exposure Notification remains as a legacy documented managed entitlement. Catalog membership does not imply a program is still accepting applications or that an omitted feature works.

## Research provenance

The public Apple entitlement index, framework guides, program support pages and request forms were cross-checked with Xcode 27.0’s bundled `DVTPortalCachedPortalCapabilities.json` (SHA-256 `b5b0346faaee515284b84e84affbb7c8f5191653eb25d90acdd9e2a09b822030`). The portal catalog supplies exact case-sensitive `profileKey` names and request metadata for managed programs not listed in the general web index. `canRequestFromPortal` and `distributionApprovalRequired` were examined alongside ordinary entries sharing the same key; privacy/user-consent requirements were not treated as developer approval. The `memory.transfer-accept` / `memory.transfer-send` portal spellings and the underscore spellings in Apple’s web documentation are listed separately as exact keys, without fuzzy matching.

## Maintenance

Recheck each primary source before changing a key or scope. Add exact keys with a capability name and evidence to `ApprovalRequiredEntitlements.swift`; update this inventory and the tests. Never replace the catalog with `com.apple.developer.*` or other prefix matching. Authenticated developer-account information may identify additional managed capabilities, but this offline signer does not access or modify that account.
